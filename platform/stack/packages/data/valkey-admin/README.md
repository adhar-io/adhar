# Valkey Admin

The Valkey project's own admin UI (`ghcr.io/valkey-io/valkey-admin:1.2.0`,
Apache-2.0) for the platform's Valkey caches, behind Keycloak SSO
(`manifests/sso.yaml`, oauth2-proxy). The app has no login of its own; the proxy
is the only way in.

| File | What it is |
| --- | --- |
| `manifests/valkey-admin.yaml` | The app (Web mode) and its ClusterIP Service |
| `manifests/sso.yaml` | Keycloak client, oauth2-proxy and its Service (generated by `hack/gen-sso.sh`) |
| `manifests/httproute.yaml` | Gateway route to the proxy, never to the app |
| `manifests/connections-sync.yaml` | Pre-added connections: discovery job, RBAC, browser bootstrap |

## Pre-added connections

When you open Valkey Admin, every Valkey created through Adhar is already on the
Connect page as `<name> (<namespace>)`, ready to connect with one click.

### Why it works this way

valkey-admin 1.2.0 stores its connection list only in the browser, in the
localStorage key `VALKEY_CONNECTIONS`
(`apps/frontend/src/state/valkey-features/connection/connectionSlice.ts`). The
server has no connections file and no API for adding one. It also takes just one
preconfigured instance (`VALKEY_HOST`/`VALKEY_PORT`), which in Web mode feeds the
metrics collector and never appears on the Connect page. In Web mode the browser
sends the password with each connect, and the server has nowhere to store or
look up a credential. That leaves the browser as the only place to seed the
list.

### How it works

1. **Discovery.** The CronJob `valkey-admin-connections-sync` in `adhar-system`
   runs every minute, and a PostSync Job runs it once after each Argo CD sync.
   It lists the hyperspike `Valkey` CRs labelled
   `app.kubernetes.io/managed-by=crossplane` that also carry
   `platform.adhar.io/cache` (from a `Cache` XR, `compositions/cache/local-valkey.yaml`)
   or `platform.adhar.io/database` (from `Database engine=valkey`). CRs being
   deleted are skipped. For each one it records:
   - host `<name>.<namespace>.svc.cluster.local`, port `6379`, from the operator's
     Service, which matches the XR's `status.host`
   - TLS from `spec.tls`, with certificate verification off (see below)
   - the password, only when `spec.anonymousAuth: false`. The job reads the
     composition's connection Secret (`<name>-cache` or `<name>-app`) to find
     `passwordSecret`/`passwordKey`, then falls back to `<name>`/`password`.
2. **Publish.** The list goes to the Secret `valkey-admin-connections`
   (`connections.js`) in `adhar-system`. It is written only when the content hash
   (annotation `adhar.io/connections-hash`) changes. If listing fails, the job
   exits non-zero and leaves the old list in place, so a failure can't empty it.
3. **Serve.** The Deployment mounts that Secret, plus `bootstrap.js` from the
   ConfigMap `valkey-admin-connections`, at `/adhar/` in the app's static
   directory. Its init container copies the image's own frontend into an
   emptyDir and adds two same-origin `<script>` tags to `index.html`. The app's
   CSP allows only `script-src 'self'`. The mount is not a subPath mount, so the
   kubelet refreshes it in place and no restart is needed.
4. **Seed.** `bootstrap.js` runs before the app's code and merges the list into
   `VALKEY_CONNECTIONS`. It records the ids it manages under
   `ADHAR_MANAGED_VALKEY_CONNECTIONS`, so it adds and updates only its own
   entries. A newly added cache is listed but not auto-connected; the user
   clicks **Connect**. Once a user has connected, the app's own auto-resume
   applies.

A new cache appears within about a minute of creation, plus up to roughly a
minute for the kubelet to refresh the volume, the next time the page loads.

### Removal

When a cache's Valkey CR is deleted, the next run drops it from the list, and
the next page load removes it from the browser. Only entries that
`bootstrap.js` added are removed. If the list can't be loaded (for example, the
Secret hasn't been written yet), the bootstrap changes nothing.

### Adding a non-Adhar instance by hand

Click **+ Add Connection** and enter its host and port, plus password and TLS if
needed. Hand-added entries stay in that browser's localStorage. The bootstrap
never edits or removes them, and other users don't see them. If you hand-add
the same host:port as an Adhar cache, the sync takes that entry over.

For a connection every user should see, create the instance through Adhar
(`kind: Cache`) instead.

### Security notes

- **Passwords reach the browser.** For a cache with `password: true`, the
  password is in `connections.js`, which is served only behind the Keycloak
  gate. It stays in that browser's localStorage until the app's first
  successful connect strips it, and comes back on the next page load. Web mode
  can't authenticate any other way. The audience is the same users who can
  already reach every passwordless cache, and FLUSHALL, through this UI.
  To keep passwords out of browsers, use either of these:
  - delete the ClusterRoleBinding `valkey-admin-connections-cache-passwords`
  - set `INCLUDE_PASSWORDS=false` on the CronJob and Job

  The caches stay listed, and the UI asks for the password on connect.
- **RBAC.** The ServiceAccount `valkey-admin-connections-sync` has:
  - `get`/`list` on `valkeys.hyperspike.io` cluster-wide (discovery)
  - `get` on Secrets cluster-wide, with no list or watch. It can only read
    Secrets it names from a Valkey CR. RBAC can't narrow this further because
    the names are created per cache at runtime. This rule sits in its own
    ClusterRole so it can be removed separately.
  - `create`, plus `get`/`update`/`patch` restricted by name, on the Secret
    `valkey-admin-connections` in `adhar-system`
- **Nothing secret is in git.** The Secret is written at runtime and carries no
  Argo CD tracking annotation, so Argo CD neither diffs nor prunes it.
- **TLS.** In-cluster caches with `tls: true` are signed by the
  `adhar-selfsigned` ClusterIssuer. valkey-admin 1.2.0 can't be given a CA
  (`caCertPath` is an unimplemented TODO upstream), so pre-added TLS
  connections use `verifyTlsCertificate: false`. They still encrypt, but they
  don't authenticate the in-cluster peer.

### Upgrading the image

The bootstrap depends on three upstream details of 1.2.0:

- the localStorage key and entry shape (`connectionDetails`, `status`,
  `connectionHistory`)
- the connection-id format `sanitizeUrl(host-port)-db<N>`
- the Connect page listing only entries with a non-empty `connectionHistory`

After changing the image tag, check these in the new tag's
`connectionSlice.ts`, `common/src/connection-id.ts` and
`components/connection/Connection.tsx`. If `index.html` no longer has a
`</head>`, the init container logs a warning and the UI runs without the
pre-added list.
