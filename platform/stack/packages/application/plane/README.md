# Plane (Community Edition)

Project and issue tracking, routed through the platform Gateway at
`https://plane.<host>`. Chart `plane/plane-ce` 1.8.0, app images `v1.4.1`.
Plane brings its own Postgres, Valkey, MinIO and RabbitMQ (`local_setup`), so
the package is self-contained.

## How you log in

Three layers, in the order a browser meets them:

| Layer | What it is | Who it accepts |
|---|---|---|
| 1. Edge | Keycloak oauth2-proxy (`manifests/sso.yaml`), client `plane` | any Keycloak user — **nobody reaches Plane without this** |
| 2. Federated login inside Plane | "Continue with Gitea" → the platform Gitea → Gitea's `keycloak` auth source | the same Keycloak user, as a real Plane account |
| 3. Credential login inside Plane | the generated instance admin | `adhar get secrets -p plane` |

```bash
adhar get secrets -p plane      # plane-admin@adhar.local + generated password
```

The admin password is generated by an ESO `Password` generator into the
`plane-admin-credentials` Secret, labelled `adhar.io/cli-secret: "true"` /
`adhar.io/package-name: plane`. Nothing is hardcoded.

### Why not plain OIDC?

**Plane Community Edition v1.4.1 ships no generic OIDC and no SAML provider.**
Inside `artifacts.plane.so/makeplane/plane-backend:v1.4.1`:

```
$ grep -ril oidc /code     # (nothing)
$ grep -ril saml /code     # (nothing)
$ ls /code/plane/authentication/provider/credentials/   email.py  magic_code.py
$ ls /code/plane/authentication/provider/oauth/         gitea.py  github.py  gitlab.py  google.py
```

and the instance payload the sign-in screen renders from
(`/api/instances/` → `plane/license/api/views/instance.py`) exposes exactly
`is_google_enabled`, `is_github_enabled`, `is_gitlab_enabled`,
`is_gitea_enabled`, `is_magic_login_enabled`, `is_email_password_enabled` —
there is no `is_oidc_enabled` to switch on. `OIDC_CLIENT_ID` and friends are a
paid-edition feature and this image does not read them from anywhere, env or
instance configuration.

So the platform uses the one federation path this edition genuinely implements:
Plane's **Gitea** OAuth provider, pointed at the platform's own Gitea — whose
sign-in is the Keycloak auth source. That makes "Continue with Gitea" a real
Keycloak login that lands a Keycloak identity in Plane
(`last_login_medium: "gitea"`), while the oauth2-proxy in front is what
actually *enforces* platform SSO.

`manifests/instance-setup.yaml` provisions the Gitea OAuth application itself
(`POST /api/v1/user/applications/oauth2` as the Gitea admin, redirect URI
`https://plane.<host>/auth/gitea/callback/`) and writes
`GITEA_CLIENT_ID` / `GITEA_CLIENT_SECRET` (Fernet-encrypted with Plane's
`SECRET_KEY`, like every other secret instance-configuration row) /
`GITEA_HOST` / `IS_GITEA_ENABLED` / `ENABLE_GITEA_SYNC`. It is best-effort: on
an install without Gitea the Job logs a skip and layers 1 and 3 still work.

Two Gitea API traps the Job has to work around, both learned the hard way:

- **`PATCH /user/applications/oauth2/{id}` regenerates the client secret** and
  returns the new one. Updating an app just to refresh its redirect URI, without
  storing what came back, silently invalidates the secret Plane holds — every
  "Continue with Gitea" then ends at
  `?error_code=5123&error_message=GITEA_OAUTH_PROVIDER_ERROR`. The Job never
  PATCHes: it deletes and re-creates, because creation is the only time Gitea
  discloses the secret (a list returns `"client_secret": ""`).
- So on every run it **probes** the stored secret first — a token exchange with a
  deliberately bogus code, since Gitea validates the secret before the code:
  `"invalid client secret"` means rotate, `"client is not authorized"` means the
  secret is still good and the app is reused untouched. That makes a stale
  secret self-healing rather than a permanent outage.

## "No authentication methods available"

That screen is rendered purely from `GET /api/instances/`. Two independent
causes have produced it here — both are now fixed in this package, and the
PostSync Job asserts against both before it exits:

1. **The instance was never set up.** Until an instance admin exists and
   `is_setup_done` is true with an auth method enabled, the payload has no
   method to offer. `manifests/instance-setup.yaml` does that on every sync,
   idempotently, and then **re-reads `/api/instances/` and exits non-zero** if
   `is_setup_done` is false or no method is enabled. A Job that exits 0 having
   enabled nothing is exactly how this shipped broken once.

2. **`/api/instances/` never reached the API.** oauth2-proxy registers a mount
   path that ends in `/` as a prefix (mux `PathPrefix`) and one *without* a
   trailing slash as an **exact** path (mux `Path`) — see
   `pkg/upstream/proxy.go:registerHandler` in oauth2-proxy v7. So
   `--upstream=http://plane-api:8000/api` served `/api` and nothing else;
   `/api/instances/` fell through to the `/` catch-all and the frontend got its
   own HTML back instead of JSON, so it believed no auth method existed. Every
   non-root upstream now ends in `/` (`hack/gen-sso.sh` appends it), and
   oauth2-proxy 301s the bare path to the slashed form. The same mistake also
   silently broke `/auth/`, `/god-mode/`, `/spaces/`, `/live/` and `/uploads/`.

A third trap sits next to them: Plane derives `CSRF_TRUSTED_ORIGINS` from
`CORS_ALLOWED_ORIGINS` (`plane/settings/common.py`), and the chart renders both
from `ingress.appHost` **even when the Ingress is disabled**. Left at the chart
default (`plane.example.com`) the sign-in page renders fine and then every
sign-in POST fails CSRF. `values.yaml` sets `ingress.appHost` to the platform
host and `ssl.externalTermination: true` for the `https://` scheme.

## Regenerating

```bash
./generate-manifests.sh      # manifests/install.yaml, from the chart + values.yaml
hack/gen-sso.sh platform/stack/packages/application/plane plane plane-web 3000 \
  --upstream=http://plane-space.adhar-system.svc.cluster.local:3000/spaces \
  --upstream=http://plane-admin.adhar-system.svc.cluster.local:3000/god-mode \
  --upstream=http://plane-api.adhar-system.svc.cluster.local:8000/api \
  --upstream=http://plane-api.adhar-system.svc.cluster.local:8000/auth \
  --upstream=http://plane-live.adhar-system.svc.cluster.local:3000/live \
  --upstream=http://plane-minio.adhar-system.svc.cluster.local:9000/uploads
```

`generate-manifests.sh` pins the chart's per-render `timestamp:` pod-template
annotation. The chart stamps the wall-clock time of the `helm template` run into
every pod template to force a rollout on `helm upgrade`; under GitOps that is
churn, and on the migrator Job (`plane-api-migrate-1`, whose name is stable) it
is fatal — `spec.template` is immutable, so ArgoCD retries `field is immutable`
forever and wedges the Application. The trade-off: a change confined to
`plane-app-vars` no longer rolls the pods by itself, so follow one with

```bash
kubectl -n adhar-system rollout restart deploy -l app.kubernetes.io/instance=plane
```

## Known rough edges (upstream chart defaults, not fixed here)

- `plane-app-secrets.SECRET_KEY` is the chart's placeholder; the backend logs a
  `SECURITY:` warning about it on every start. Rotating it invalidates every
  Fernet-encrypted instance-configuration row (including the Gitea client
  secret) — the setup Job re-creates those, but sessions are lost.
- MinIO ships with `admin`/`password` from the chart. It is only reachable
  in-cluster and via `/uploads/` behind the proxy.
