# Adhar Roadmap

Direction, not commitment — sequencing follows community needs. Discuss on [GitHub Discussions](https://github.com/adhar-io/adhar/discussions).

The destination is fixed: the best open-source Internal Developer Platform — one command to a complete, production-grade, customizable platform on any infrastructure. The [Architecture](ARCHITECTURE.md) describes the target design (topologies T1→T3); **this roadmap is the main tracker** — every capability is listed under its phase with its current status.

**Legend**: ✅ implemented and exercised · 🟡 implemented, needs live verification/hardening · 🔴 built but blocked on a decision or an external dependency · 🔜 designed, not yet built

## Phase 1 — Single-Cluster Production (T2) ✅ VERIFIED (DigitalOcean, 2026-09)

Make one managed cluster a defensible production platform. Every item below was exercised on a real DigitalOcean cluster (kubeadm, HA mode, 1 control plane + 10 workers, full production catalogue) in September 2026; the one 🟡 left is the node autoscaler, whose live scale-up/down run still needs a DigitalOcean token (the cloud API path is the same one `adhar cluster scale` already proved).

- ✅ **Self-managed clusters on raw cloud compute (kubeadm) — DigitalOcean live-verified**: all six providers (AWS EC2, Azure VMs, GCP GCE, DigitalOcean droplets, Civo instances, custom BYO hosts) provision plain Ubuntu machines and bootstrap Kubernetes with kubeadm over SSH — containerd, kube-proxy skipped (Cilium from the platform bootstrap replaces it, matching the Kind flow); managed services opt-in via `useManagedK8s: true` with otherwise identical behaviour — DOKS and Civo k3s live-exercised, EKS/AKS/GKE built 2026-09-17 (`<cloud>/managed.go`: create, kubeconfig, node groups, scale, upgrade, health, delete through each managed API). Compute mode on AWS/Azure/GCP/Civo/custom gained the cloud-controller-manager, CSI driver + default StorageClass and the CSI startup-taint toleration through one shared integration runner (`platform/providers/cloudintegration.go`, pinned upstream charts/manifests) — built, awaiting a live bring-up per cloud. Live on DO (2026-09): **clean `--recreate` → 1 control plane + 10 workers + full platform bootstrap in ~18 min**, worker scale-up (join) / scale-down (drain), LB + wildcard TLS + DNS all automatic. Node prep now also hardens the node itself — static upstream resolvers (the systemd-resolved stub dying wedged every containerd image pull cluster-wide) and raised inotify/file-descriptor limits (controller managers were dying with "too many open files" on dense nodes). Single control-plane today (HA control planes with LB + stacked etcd are the next step)
- ✅ **In-cluster controllers (DigitalOcean live-verified 2026-09)**: `adhar controller` runs the manager as a Deployment (leader election, health probes); installed by `adhar up --in-cluster` and by default on cloud bootstraps. It runs the released image matching the CLI (`ghcr.io/adhar-io/adhar:<version>`; dev builds track `:latest`) — verified holding the lease and reconciling the DataPlane API on the cloud cluster (dev code exercised via a Harbor-hosted build of the same image)
- ✅ **HA mode end-to-end (DigitalOcean live-verified 2026-09)**: `enableHAMode` flows config → `AdharPlatform` CR → HA manifest variants: ArgoCD application-controller ×2, redis-ha ×3 + haproxy ×3, server/repo-server HPAs + PDBs; Gitea on a bootstrap-phase CNPG cluster (`gitea-db`, 2 instances, no bundled PostgreSQL), Keycloak on CNPG (`keycloak-db`, 2 instances in HA via the seed-time template); Crossplane HA variant selected. Fixed on the way: the HA ArgoCD variant had `server.insecure: false` (redirect loop behind the Gateway). Remaining: Gitea itself is 1 replica behind a PDB; HA *control planes* (multi-master) are still the next step
- ✅ **Production edge (DigitalOcean live-verified 2026-09)**: cloud Gateway variant (LoadBalancer, wildcard listener) with the issuer chosen by the platform spec; DNS provider derived from the cloud (or `globalSettings.dnsProvider`), credentials materialised by the CLI into the `adhar-dns-provider` Secret; external-dns publishes every HTTPRoute hostname in the platform zone; cert-manager issues the `*.<host>` wildcard via DNS-01 (`adhar-letsencrypt-dns`, rendered per provider from `cluster-issuers.yaml.tmpl`); the whole stack is templated at seed time (`*.yaml.tmpl`) with no hardcoded host/email/cloud; console reachable at `https://console.<host>` on a real domain
- ✅ **SSO by default**: Keycloak OIDC wired into ArgoCD, Gitea, Grafana, Console, Kargo (native), and every other platform UI through a generated oauth2-proxy front (`hack/gen-sso.sh` → `sso.yaml`); Keycloak clients are provisioned generically from labelled ConfigMaps (`adhar.io/keycloak-client`) by the config job plus a 5-minute reconcile CronJob, so a new package gets SSO by shipping one ConfigMap; `credential-rotation` rotates bootstrap credentials into secrets-backend break-glass (OpenBao in production, or Vault) and the foundation/`adhar upgrade` honour the rotated `gitea-credential`
- ✅ **Applications consume platform capabilities, never bundle their own**: one Strimzi **Kafka in KRaft mode** (`adhar-kafka`, no ZooKeeper anywhere), one MinIO (per-app buckets provisioned from `data/minio/values.yaml`), CNPG for PostgreSQL, Valkey for cache, OpenSearch for search, ClickHouse Keeper where a chart wants ZooKeeper. Bundled subcharts are stripped in each package's `generate-manifests.sh` so the wiring survives chart regeneration — this removed a duplicate Kafka+ZooKeeper (PostHog) and a duplicate MinIO (Kubeflow Pipelines), both of which had also rotted upstream (deleted Bitnami / gcr.io images)
- ✅ **Backup/DR (DigitalOcean live-verified 2026-09)**: Velero Schedules (daily platform / weekly cluster) with the node agent deployed and file-system backups on by default + CNPG WAL archiving and daily base backups for platform databases, all into the platform MinIO (`adhar-backups`; Velero under its own `velero/` prefix, CNPG under `cnpg/`). Drill run: on-demand backup → restore into a scratch namespace recreated the Kargo project intact. Off-cluster object storage (DO Spaces/S3) is a BackupStorageLocation swap; runbook in [Production §5](PRODUCTION.md#5-backup-and-disaster-recovery)
- ✅ **Node autoscaling — live-verified on DigitalOcean (2026-09-12), both directions**: `environments[].autoscaling` turns the worker count into a range, driven by a platform-native controller in `adhar-controller-manager` (the upstream cluster-autoscaler has no provider for self-managed kubeadm on raw compute). A cluster created with **3** workers and `maxWorkers: 10` grew itself to **9** while the catalogue synced — each step naming the pod that forced it, e.g. `1 pod(s) unschedulable for capacity (e.g. adhar-system/oncall-redis-master-0); adding a worker (4/10)` — then removed one when idle: `cluster idle for 1h40m46s (cpu=21% memory=27%); removing adhar-dev-workers-9 (9→8 workers)`, drained through the eviction API with PDBs honoured, leaving neither Node nor droplet. Both refusal guards were observed too: the cooldown between moves, and `no worker is safe to drain: … pod adhar-system/affinity-assistant-…` when the emptiest node holds a ReadWriteOnce volume. The run also corrected the trigger set — on DigitalOcean the first capacity wall is the **7 block-volumes-per-droplet** limit (`exceed max volume count`), not CPU or memory, so that is now a scale-up signal while `volume node affinity conflict` still is not. Everything is reported on `AdharPlatform.status.autoscaling` and as Events. Configuration: [DigitalOcean §4.1](DIGITALOCEAN_PROVIDER.md#41-autoscaling)
- ✅ **Upgrade story (DigitalOcean live-verified 2026-09)**: `adhar upgrade` converges the foundation through the real reconcilers (now including the Crossplane control-plane configuration — XRDs, Compositions, Functions, provider packages, Operations — re-applied on every upgrade), diffs the local stack against the GitOps repos (`--diff-only`, `--yes`), pushes and refreshes on confirm; exercised five times in a row to roll fixes onto the live cluster

- ✅ **Workload clusters via GitOps (DigitalOcean live-verified 2026-09-12)**: a `CompositeCluster` XR provisioned a real DOKS cluster (apply → `Ready` in ~11 min), Crossplane wrote its kubeconfig, and the platform auto-registered it with ArgoCD as `cluster-wl-blr1` carrying `adhar.io/cluster|dataplane|dataplane-mode` — which is what the thin workload profile selects on, landing metrics-server, kyverno, kyverno-policies, alloy and external-secrets 5/5 Healthy on it ~3 min later. EKS/GKE/AKS/Civo registration remains render-verified only. Recipe: [DigitalOcean §4.4](DIGITALOCEAN_PROVIDER.md#44-workload-clusters-doks-through-crossplane)
- ✅ **Thin workload-cluster profile (live-verified 2026-09)**: `adhar-appset-workload.yaml` deploys the agent set (kyverno + policies, alloy, the **external-secrets** agent, and metrics-server on planes with real kubelets — vcluster planes serve `metrics.k8s.io` through vcluster's host proxy instead) onto every ArgoCD-registered data plane (`adhar.io/cluster` label, stamped by both registration paths); monitoring CRs are excluded on data planes (no Prometheus Operator there) and the hub endpoints written by the DataPlane controller are respected (`RespectIgnoreDifferences`). Verified Healthy on the vcluster plane
- ✅ **Observability out of the box**: every package that exposes metrics ships a ServiceMonitor/PodMonitor and a Grafana dashboard (`kube-prometheus/manifests/dashboard-*.yaml`), Prometheus selects all monitors cluster-wide; Alloy ships metrics/logs/traces (cluster-labeled) to hub endpoints from the `observability-hub` ConfigMap; mimir/loki/tempo ingestion HTTPRoutes (SSO-fronted with bearer passthrough for spokes)
- ✅ **Cilium Cluster Mesh — live-verified on DigitalOcean (2026-09-12); SPIFFE/SPIRE deliberately not deployed**: `adhar-mgmt` (cluster id 1, Pod CIDR `10.244.0.0/16`) meshed with `adhar-test` (id 2, `10.245.0.0/16`) — `cilium clustermesh status` reports all nodes connected on both sides, and a global service serves traffic both ways. Getting there fixed ten things that had never executed: the Cilium cluster name/id and the Pod CIDR were hardcoded constants (so every Adhar cluster claimed the same identity and overlapping pods), the clustermesh-apiserver manifest was applied by no code path and its Service was unreachable `ClusterIP`, its TLS was signed by a different CA than the one in use, and the connect Job ran `sh -c` on a shell-less image and needed a Helm release Adhar does not have (the join is now declarative; the Job only verifies). "Mesh-ready identity" therefore means a unique cluster name+id and one shared CA; workload-to-workload mutual authentication is **not** available and is not claimed. ## Phase 3 — Developer Experience & Ecosystem (IN PROGRESS)

From platform to product.

- ✅ **Paved-road CI (Tekton `app-ci`)**: the supply-chain package ships the CI EventListener + pipelines, driven by each service's `.adhar/app.yaml`
  - **Pipeline**: Gitea webhook → buildpacks/Dockerfile build → cosign sign → trivy scan → Harbor → GitOps version-bump
  - **Image tags**: every build now lands in Harbor under `:latest` **and** `:<commit sha>`
  - **PR builds**: a `pull_request` trigger builds the head of any PR labelled `preview` (no writeback), so per-PR previews deploy real code
  - **Library releases** publish to Nexus — both pipelines **re-verified end to end on DigitalOcean (2026-09-13)**: `release-adhar-ui` and `release-adhar-kit` each complete **6/6 tasks with 0 failures** (clone → build → test → lint → trivy scan → Nexus publish)
    - **They were broken, and the cause was one mistake with three faces**: hardening the Tasks to `runAsUser: 1000` without hardening the *shared* Task they all depend on. `git-clone-gitea` had **no `securityContext` at all**, so it ran as **root** — the builds could read its clone but not write inside it (`failed to create directory '…/node_modules': Permission denied`). Fixing that surfaced two more of the same shape: trivy died on `mkdir /.cache` because it derives its cache from `$HOME`, which is `/` in that image (and the 113 MiB DB downloads *first*, so it reads like a network fault), and `corepack enable` died symlinking into `/usr/local/bin`. Each was invisible until the previous one was fixed
    - **`fsGroup` does not rescue this**: with `fsGroupChangePolicy: OnRootMismatch` the kubelet checks only the volume *root*, finds the group already correct, and skips the recursive pass — so anything a different uid wrote deeper keeps its ownership. Tekton's `default-pod-template` now uses `Always`
    - **The lesson worth keeping**: every stage that shares a workspace must agree on who it is. A pipeline whose stages disagree fails at whichever stage happens to write next, which makes it look like a different bug each time
  - **Run retention now exists** (`application/tekton/manifests/pipelinerun-pruner.yaml`): upstream's pruner ships with the Tekton *Operator*, which this platform does not install, so runs accumulated without limit — and because ArgoCD tracks PipelineRuns as children of the Application that owns the Pipelines, **one historical failure kept that Application Degraded indefinitely**, long after the cause was fixed. A CronJob keeps the 3 most recent completed runs per pipeline, never touches a run still executing, and lets ownerReferences collect the TaskRuns and pods
  - The Jenkins X / Lighthouse layer was removed (ADR-0018 superseded)
- ✅ **Preview environments (live run verified 2026-09-13)**: now a real package, not an example — `application/preview-environments` (enabled in the local, production and gitops sets) gives every PR labelled `preview` its own namespace, image and hostname. ADR-0017 records the deltas; [User Guide §5](USER_GUIDE.md#5-preview-a-pull-request) documents the flow
  - **How it works**: ONE org-wide ApplicationSet — a matrix of the Gitea `scmProvider` generator (every repo shipping `preview/kustomization.yaml`) × the Gitea `pullRequest` generator (every open PR labelled `preview`) — produces Application `<repo>-pr-<n>` that syncs the PR head SHA into namespace `preview-<repo>-<n>` with the image tag pinned to that SHA and the HTTPRoute rewritten to `<repo>-pr-<n>.<domain>`
  - **Guardrails and cleanup**: a Kyverno policy stamps a ResourceQuota + LimitRange on every preview namespace, and closing the PR prunes the Application and its resources, and its namespace too when the overlay declares the Namespace as a managed resource (no reaper job)
  - **Supporting changes**: `app-ci` was extended to build PR heads and tag every image `:latest` **and** `:<commit sha>`, and the golden-path skeletons ship the `preview/` overlay
  - **By design**: previews are deliberately unauthenticated-but-internal (a per-PR hostname would need a per-PR OIDC client)
  - **LIVE-VERIFIED on DigitalOcean (2026-09-13)** — a throwaway `adhar/preview-demo` Gitea repo with a `preview/kustomization.yaml`, one PR labelled `preview`:
    - the ApplicationSet generated `preview-demo-pr-1` in under 30 s
    - it created namespace `preview-preview-demo-1` labelled `adhar.io/plane: preview` + `adhar.io/preview: true`, and Kyverno stamped `preview-quota` and `preview-limits` on it
    - **the PR head was what deployed, not the base branch** (the PR's `replicas: 2` change was live)
    - adding an HTTPRoute to the overlay produced `preview-demo-pr-1.platform.adhar.io`, which answered **HTTP 200**
    - closing the PR pruned the Application and every resource it owned within ~60 s, with no reaper job
  - **This uncovered a fatal bug that had to be fixed first — the wrong ArgoCD finalizer**:
    - the Application template set `resources-finalizer.argoproj.io`, but ArgoCD honours only `resources-finalizer.argocd.argoproj.io` — with the `argocd.` segment
    - the API server stores any finalizer string, so the short name was accepted and then removed by nobody: the ApplicationSet controller logged `generated 0 applications` and `Deleted application` every single minute while the Application sat in Terminating for 12+ minutes (`process_finalizers_ms=0`) and **nothing was ever pruned**
    - the same wrong name was in all four main ApplicationSets (`adhar-appset-{local,production,gitops,workload}.yaml`) and in the DataPlane controller's vcluster Application, so deleting *any* platform Application would have hung the same way; all six are corrected and the Go path now uses `globals.ArgoCDResourcesFinalizer`
  - **One caveat worth keeping in mind rather than fixing**: the *namespace* is pruned only when the overlay declares it as a managed resource — a namespace created solely by `CreateNamespace=true` is unmanaged and stays behind. The appset's own comment says this and the four golden-path skeletons all declare their Namespace; a hand-rolled overlay that omits it leaves an empty namespace
- ✅ **Supply-chain policies (enforce pack live in production, 2026-09-13)**: the ADR-0019 staged rollout is now a real switch, not a comment — the three policies ship twice (Audit everywhere, Enforce as a one-line flip), and the enforce pack is now enabled and verified live in the production profile
  - **Two packs, identical rules**: signature verification, no-`:latest` and registry allowlist moved out of `kyverno-policies` into their own `security/supply-chain-policies` package and ship **twice** — `manifests/audit/` (enabled everywhere, the default) and `manifests/enforce/` (wired `enabled: "false"`, the knob) — identical rules differing only in `failureAction` (plus digest pinning, which Kyverno forbids on a non-enforcing rule), so **Audit findings predict exactly what Enforce would block**. Enforcing an environment is one line in `adhar-appset-<env>.yaml` + the mirrored `environments/<env>/config.yaml`; policy names carry an `-enforce` suffix so both packs coexist
  - **The attestor now matches what the platform actually produces**: the Tekton `cosign-sign` Task signs **with a key** (`--key=k8s://adhar-system/cosign-key --tlog-upload=false`) from a durable, platform-owned keypair generated once by the `cosign-keygen` Sync-hook Job — so the policy reads that Secret via a `keys.secret` attestor with `rekor.ignoreTlog: true` (the previous policy pointed at `rekor.sigstore.dev`, which would have failed *every* platform-built image the moment it enforced), with the GitHub Actions **keyless** identity kept as an `any`-alternative (`count: 1`) for the `ghcr.io/adhar-io/*` images `.goreleaser.yaml` `docker_signs` signs
  - **An Enforce flip cannot brick the platform**: `adhar-system`/`kube-system` (and the rest of the platform namespaces, plus anything labelled `adhar.io/plane: control`) are excluded from every rule, twice over — by name and by label
  - **Scanning and webhook placement**: scanning in the pipeline is a Tekton `trivy-scan` Task running `aquasec/trivy` directly, so the gate does not depend on the `security/trivy` operator package (which stays wired-but-disabled in every profile — an earlier draft of this line claimed it was enabled in production; it is not); cosign's policy-controller runs in the shared `adhar-system` namespace like every other package (ADR-0011) — the `Secret/webhook-certs` collision it used to have with Tekton is resolved by renaming *Tekton's* secret through `WEBHOOK_SECRET_NAME` and pinning its `WEBHOOK_PORT`, and the one package that cannot follow (kpack/buildpack hardcodes the same secret name in its binary) keeps `kpack-system`
  - **The drill** is `hack/verify-supply-chain.sh`: throwaway cosign keypair → two tiny public images copied into the platform Harbor → sign one → Enforce ClusterPolicy scoped to a scratch namespace with `failurePolicy: Fail` → assert unsigned DENIED / signed ADMITTED → clean up everything
  - **The drill has now been run, twice, on a live DigitalOcean cluster (2026-09-13) and PASSES**: Kyverno reaches `harbor.platform.adhar.io`, parses a key-based cosign signature made with `--tlog-upload=false`, and enforces it at admission — unsigned image DENIED, signed image ADMITTED — which is exactly the signature the Tekton `cosign-sign` Task produces, so `security/supply-chain-policies/manifests/enforce` is safe to enable. Cleanup verified complete (project 404, namespace gone) and a second consecutive run passed identically

## Cross-Cutting Commitments

- **No breaking changes without an ADR** and a documented migration
- **Local–production parity is sacred** — nothing lands in T2/T3 that can't be exercised (scaled down) in T1
- **Every feature ships with docs** — the [docs set](README.md) is part of the definition of done
- **APIs graduate deliberately**: `v1alpha1` → `v1beta1` once controllers are in-cluster and covered by e2e
- **Provider parity is measured, not assumed**: DigitalOcean's self-managed worker lifecycle is the shared implementation (`platform/providers/kubeadm.go`) every raw-compute provider scales through; what each cloud has beyond it (CCM, CSI, upgrade) is a per-row entry in [PROVIDER_GUIDE §2.1](PROVIDER_GUIDE.md), and a row only turns ✅ live after a bring-up on that cloud
- **Local engines are a CI matrix**: the e2e bootstrap runs on Docker *and* Podman on every push (`make e2e ENGINE=podman` locally); a change that only breaks one engine fails the build
- **🟡 → ✅ requires a live run**: Phase 1/2 items graduate only after a real cloud provisioning + multi-cluster exercise; a standing verification checklist lives with each phase's PRs
- **A green Application is not a working feature.** Repeatedly this cycle, something was reported Healthy or Synced while the capability behind it was dead: `tools/list` advertised `promql` while the Prometheus URL resolved to nothing; the `adhar-ai-bot` ExternalSecret's absence left the agent's entire write path inert; every library pipeline was red for a filesystem-ownership reason no manifest review would show. Verification means exercising the capability — a real completion, a real tool call, a pipeline that publishes — not reading a status field
- **"Configured correctly" is not the same as "working", and Grafana will tell you the first.** Loki's `limits_config.volume_enabled: true` was set in values, in the rendered manifest and in the live ConfigMap — while `loki-0` had been in CrashLoopBackOff for 29 restarts with a full 10Gi volume (`err="short write"`, store module failed to initialise). The user-visible symptoms were *"no Loki datasource configured"* and *"Log volume has not been configured"*: two **configuration** messages for a backend that was simply dead. Check the process before the config
- **A repair must not be ordered behind the thing it repairs.** Two separate packages shipped fixes that could never execute: PostHog's `crash_log` Job ran PostSync, so it needed the sync it was fixing to succeed first; Airbyte's bootloader ran PreSync, ahead of its own ServiceAccount. Both looked correct in review. When a fix is ordered relative to a failure, state which wave or phase it lands in and why that is reachable
- **Hardening one Task hardens none of them.** Adding `runAsUser` to the Tasks that build, while leaving the shared clone Task as root, produced three distinct-looking failures from one cause. Every stage sharing a workspace must agree on its identity
