# Adhar Roadmap

Direction, not commitment — sequencing follows community needs. Discuss on [GitHub Discussions](https://github.com/adhar-io/adhar/discussions).

The destination is fixed: the best open-source Internal Developer Platform — one command to a complete, production-grade, customizable platform on any infrastructure. The [Architecture](ARCHITECTURE.md) describes the target design (topologies T1→T3); **this roadmap is the main tracker** — every capability is listed under its phase with its current status.

**Legend**: ✅ implemented and exercised · 🟡 implemented, needs live verification/hardening · 🔴 built but blocked on a decision or an external dependency · 🔜 designed, not yet built

## Phase 1 — Single-Cluster Production (T2) ✅ VERIFIED (DigitalOcean, 2026-09)

Make one managed cluster a defensible production platform. Every item below was exercised on a real DigitalOcean cluster (kubeadm, HA mode, 1 control plane + 10 workers, full production catalogue) in September 2026; the one 🟡 left is the node autoscaler, whose live scale-up/down run still needs a DigitalOcean token (the cloud API path is the same one `adhar cluster scale` already proved).

- ✅ **Self-managed clusters on raw cloud compute (kubeadm) — DigitalOcean live-verified**: all six providers (AWS EC2, Azure VMs, GCP GCE, DigitalOcean droplets, Civo instances, custom BYO hosts) provision plain Ubuntu machines and bootstrap Kubernetes with kubeadm over SSH — containerd, kube-proxy skipped (Cilium from the platform bootstrap replaces it, matching the Kind flow); managed services (DOKS, Civo k3s) opt-in via `useManagedK8s: true` with otherwise identical behaviour. Live on DO (2026-09): **clean `--recreate` → 1 control plane + 10 workers + full platform bootstrap in ~18 min**, worker scale-up (join) / scale-down (drain), LB + wildcard TLS + DNS all automatic. Node prep now also hardens the node itself — static upstream resolvers (the systemd-resolved stub dying wedged every containerd image pull cluster-wide) and raised inotify/file-descriptor limits (controller managers were dying with "too many open files" on dense nodes). Single control-plane today (HA control planes with LB + stacked etcd are the next step)
- ✅ **In-cluster controllers (DigitalOcean live-verified 2026-09)**: `adhar controller` runs the manager as a Deployment (leader election, health probes); installed by `adhar up --in-cluster` and by default on cloud bootstraps. It runs the released image matching the CLI (`ghcr.io/adhar-io/adhar:<version>`; dev builds track `:latest`) — verified holding the lease and reconciling the DataPlane API on the cloud cluster (dev code exercised via a Harbor-hosted build of the same image)
- ✅ **HA mode end-to-end (DigitalOcean live-verified 2026-09)**: `enableHAMode` flows config → `AdharPlatform` CR → HA manifest variants: ArgoCD application-controller ×2, redis-ha ×3 + haproxy ×3, server/repo-server HPAs + PDBs; Gitea on a bootstrap-phase CNPG cluster (`gitea-db`, 2 instances, no bundled PostgreSQL), Keycloak on CNPG (`keycloak-db`, 2 instances in HA via the seed-time template); Crossplane HA variant selected. Fixed on the way: the HA ArgoCD variant had `server.insecure: false` (redirect loop behind the Gateway). Remaining: Gitea itself is 1 replica behind a PDB; HA *control planes* (multi-master) are still the next step
- ✅ **Production edge (DigitalOcean live-verified 2026-09)**: cloud Gateway variant (LoadBalancer, wildcard listener) with the issuer chosen by the platform spec; DNS provider derived from the cloud (or `globalSettings.dnsProvider`), credentials materialised by the CLI into the `adhar-dns-provider` Secret; external-dns publishes every HTTPRoute hostname in the platform zone; cert-manager issues the `*.<host>` wildcard via DNS-01 (`adhar-letsencrypt-dns`, rendered per provider from `cluster-issuers.yaml.tmpl`); the whole stack is templated at seed time (`*.yaml.tmpl`) with no hardcoded host/email/cloud; console reachable at `https://console.<host>` on a real domain
- ✅ **SSO by default**: Keycloak OIDC wired into ArgoCD, Gitea, Grafana, Console, Kargo (native), and every other platform UI through a generated oauth2-proxy front (`hack/gen-sso.sh` → `sso.yaml`); Keycloak clients are provisioned generically from labelled ConfigMaps (`adhar.io/keycloak-client`) by the config job plus a 5-minute reconcile CronJob, so a new package gets SSO by shipping one ConfigMap; `credential-rotation` rotates bootstrap credentials into secrets-backend break-glass (OpenBao in production, or Vault) and the foundation/`adhar upgrade` honour the rotated `gitea-credential`
- ✅ **Applications consume platform capabilities, never bundle their own**: one Strimzi **Kafka in KRaft mode** (`adhar-kafka`, no ZooKeeper anywhere), one MinIO (per-app buckets provisioned from `data/minio/values.yaml`), CNPG for PostgreSQL, Valkey for cache, OpenSearch for search, ClickHouse Keeper where a chart wants ZooKeeper. Bundled subcharts are stripped in each package's `generate-manifests.sh` so the wiring survives chart regeneration — this removed a duplicate Kafka+ZooKeeper (PostHog) and a duplicate MinIO (Kubeflow Pipelines), both of which had also rotted upstream (deleted Bitnami / gcr.io images)
- ✅ **Backup/DR (DigitalOcean live-verified 2026-09)**: Velero Schedules (daily platform / weekly cluster) with the node agent deployed and file-system backups on by default + CNPG WAL archiving and daily base backups for platform databases, all into the platform MinIO (`adhar-backups`; Velero under its own `velero/` prefix, CNPG under `cnpg/`). Drill run: on-demand backup → restore into a scratch namespace recreated the Kargo project intact. Off-cluster object storage (DO Spaces/S3) is a BackupStorageLocation swap; runbook in [Production §5](PRODUCTION.md#5-backup-and-disaster-recovery)
- ✅ **Node autoscaling — live-verified on DigitalOcean (2026-09-12), both directions**: `environments[].autoscaling` turns the worker count into a range, driven by a platform-native controller in `adhar-controller-manager` (the upstream cluster-autoscaler has no provider for self-managed kubeadm on raw compute). A cluster created with **3** workers and `maxWorkers: 10` grew itself to **9** while the catalogue synced — each step naming the pod that forced it, e.g. `1 pod(s) unschedulable for capacity (e.g. adhar-system/oncall-redis-master-0); adding a worker (4/10)` — then removed one when idle: `cluster idle for 1h40m46s (cpu=21% memory=27%); removing adhar-dev-workers-9 (9→8 workers)`, drained through the eviction API with PDBs honoured, leaving neither Node nor droplet. Both refusal guards were observed too: the cooldown between moves, and `no worker is safe to drain: … pod adhar-system/affinity-assistant-…` when the emptiest node holds a ReadWriteOnce volume. The run also corrected the trigger set — on DigitalOcean the first capacity wall is the **7 block-volumes-per-droplet** limit (`exceed max volume count`), not CPU or memory, so that is now a scale-up signal while `volume node affinity conflict` still is not. Everything is reported on `AdharPlatform.status.autoscaling` and as Events. Configuration: [DigitalOcean §4.1](DIGITALOCEAN_PROVIDER.md#41-autoscaling)
- ✅ **Upgrade story (DigitalOcean live-verified 2026-09)**: `adhar upgrade` converges the foundation through the real reconcilers (now including the Crossplane control-plane configuration — XRDs, Compositions, Functions, provider packages, Operations — re-applied on every upgrade), diffs the local stack against the GitOps repos (`--diff-only`, `--yes`), pushes and refreshes on confirm; exercised five times in a row to roll fixes onto the live cluster

The management cluster earns its name, and every item in this phase is now live-verified on DigitalOcean (2026-09): control-plane/data-plane separation (vcluster + adopt), **workload clusters via GitOps (a real DOKS cluster provisioned and ArgoCD-registered by a `CompositeCluster` XR, 2026-09-12)**, the thin workload profile, observability out of the box, and **Cilium Cluster Mesh between two real self-managed Adhar clusters (2026-09-12)**. The one thing deliberately *not* delivered here is SPIFFE/SPIRE workload identity — see the Cluster Mesh entry for why that is a decision rather than a gap.

- ✅ **Control-plane / data-plane separation (vcluster + adopt live-verified 2026-09)** ([ADR-0023](adr/0023-control-dataplane-separation.md), [plan](design/0023-control-dataplane-separation.md)): the `DataPlane` API and controller are real end-to-end for `mode: vcluster` (the controller installs a vcluster through an ArgoCD Application, mirrors its kubeconfig, registers it with ArgoCD, wires the observability hub, and reports `Ready`) and `mode: adopt` (existing kubeconfig); both reached `Ready=True` on the cloud cluster, the thin profile landed on the plane, `adhar get dataplanes` lists them and `adhar get status` shows the fleet roll-up now kept on `AdharPlatform.status.fleet`. `mode: composite` builds an XRD-valid `CompositeCluster` (composition selection under `spec.crossplane.*`, the Crossplane v2 form); the XR path it authors is now live-proven on DOKS (see *Workload clusters via GitOps*), so what is still unexercised is only the controller wrapper — a `DataPlane` with `mode: composite` driving that XR and reporting `Ready`. The controller watches only core types, so it is registered unconditionally (no more cache-sync death). The mesh phase is now live-proven too (see *Cilium Cluster Mesh* below), and finalize no longer fights the workload ApplicationSet — it strips the plane's selector labels off the ArgoCD cluster secret before deleting its Applications, so they stop being regenerated as fast as they are deleted. Still 🟡 inside this item: Sveltos placement in the `environments` repo, `control-plane-no-apps` shipped but disabled, no envtest yet
- ✅ **Workload clusters via GitOps (DigitalOcean live-verified 2026-09-12)**: a `CompositeCluster` XR provisioned a real DOKS cluster (apply → `Ready` in ~11 min), Crossplane wrote its kubeconfig, and the platform auto-registered it with ArgoCD as `cluster-wl-blr1` carrying `adhar.io/cluster|dataplane|dataplane-mode` — which is what the thin workload profile selects on, landing metrics-server, kyverno, kyverno-policies, alloy and external-secrets 5/5 Healthy on it ~3 min later. Teardown removed the cluster and both droplets with no paid resource left. Three fixes made it possible: ProviderConfigs were **never applied on any fresh cluster** (a NoMatch error was treated as skip-with-warning and the one-shot `ControlPlaneApplied` flag then blocked the retry forever — so nothing could ever be provisioned), namespaced `.m` managed resources reject `spec.deletionPolicy` (retention is `managementPolicies` without Delete), and the composition's fallback DOKS version slug had expired. Known rough edge: deleting the XR removes the ArgoCD registration Secret at the same instant as the cluster, so that cluster's Applications hang `Terminating` on a finalizer that can no longer reach the plane. EKS/GKE/AKS/Civo registration remains render-verified only. Recipe: [DigitalOcean §4.4](DIGITALOCEAN_PROVIDER.md#44-workload-clusters-doks-through-crossplane)
- ✅ **Thin workload-cluster profile (live-verified 2026-09)**: `adhar-appset-workload.yaml` deploys the agent set (kyverno + policies, alloy, the **external-secrets** agent, and metrics-server on planes with real kubelets — vcluster planes serve `metrics.k8s.io` through vcluster's host proxy instead) onto every ArgoCD-registered data plane (`adhar.io/cluster` label, stamped by both registration paths); monitoring CRs are excluded on data planes (no Prometheus Operator there) and the hub endpoints written by the DataPlane controller are respected (`RespectIgnoreDifferences`). Verified Healthy on the vcluster plane
- ✅ **Observability out of the box**: every package that exposes metrics ships a ServiceMonitor/PodMonitor and a Grafana dashboard (`kube-prometheus/manifests/dashboard-*.yaml`), Prometheus selects all monitors cluster-wide; Alloy ships metrics/logs/traces (cluster-labeled) to hub endpoints from the `observability-hub` ConfigMap; mimir/loki/tempo ingestion HTTPRoutes (SSO-fronted with bearer passthrough for spokes)
- ✅ **Cilium Cluster Mesh — live-verified on DigitalOcean (2026-09-12); SPIFFE/SPIRE deliberately not deployed**: `adhar-mgmt` (cluster id 1, Pod CIDR `10.244.0.0/16`) meshed with `adhar-test` (id 2, `10.245.0.0/16`) — `cilium clustermesh status` reports all nodes connected on both sides, and a global service serves traffic both ways. Getting there fixed ten things that had never executed: the Cilium cluster name/id and the Pod CIDR were hardcoded constants (so every Adhar cluster claimed the same identity and overlapping pods), the clustermesh-apiserver manifest was applied by no code path and its Service was unreachable `ClusterIP`, its TLS was signed by a different CA than the one in use, and the connect Job ran `sh -c` on a shell-less image and needed a Helm release Adhar does not have (the join is now declarative; the Job only verifies). Two teardown bugs were leaking a billable load balancer and stripping shared role tags off other clusters' droplets. Operational rule: meshed clusters must **share a VPC** (or use a LoadBalancer-typed apiserver) because on DigitalOcean node ports answer only on the private NIC. **SPIRE is absent on purpose** — it starved the Cilium operator's Gateway controller, and upstream marks that path deprecated in 1.20 for removal in 1.21 (the platform runs 1.20). "Mesh-ready identity" therefore means a unique cluster name+id and one shared CA; workload-to-workload mutual authentication is **not** available and is not claimed. Setup and requirements: [DigitalOcean §4.5](DIGITALOCEAN_PROVIDER.md#45-cilium-cluster-mesh-between-two-adhar-clusters)
- ✅ **Environment promotion (live-verified 2026-09)**: Kargo pipeline (Warehouse on the `environments` repo; staging auto-promotes, production requires approval; a promotion is a Git commit). Drill: a commit to `development/` produced Freight, staging auto-promoted and `promote: development -> staging` landed in the repo while production stayed unpromoted. Fixed on the way: Kargo ≥1.3 `ProjectConfig`, path-prefix vs glob `includePaths`, credentials over the in-cluster HTTP Gitea
- ✅ **Cluster reconstructability SLO (live-verified 2026-09)**: monthly drill CronOperation + observer WatchOperation measuring time-to-Ready against the 1-hour SLO (Crossplane Operations enabled on the running platform). ## Phase 3 — Developer Experience & Ecosystem (IN PROGRESS)

From platform to product.

- ✅ **Paved-road CI (Tekton `app-ci`)**: the supply-chain package ships the CI EventListener + pipelines (Gitea webhook → buildpacks/Dockerfile build → cosign sign → trivy scan → Harbor → GitOps version-bump), driven by each service's `.adhar/app.yaml` — every build now lands in Harbor under `:latest` **and** `:<commit sha>`, and a `pull_request` trigger builds the head of any PR labelled `preview` (no writeback) so per-PR previews deploy real code; library releases publish to Nexus (`adhar-kit`, `adhar-ui` verified green); the Jenkins X / Lighthouse layer was removed (ADR-0018 superseded)
- 🟡 **Preview environments**: now a real package, not an example — `application/preview-environments` (enabled in the local, production and gitops sets) runs ONE org-wide ApplicationSet: a matrix of the Gitea `scmProvider` generator (every repo shipping `preview/kustomization.yaml`) × the Gitea `pullRequest` generator (every open PR labelled `preview`), producing Application `<repo>-pr-<n>` that syncs the PR head SHA into namespace `preview-<repo>-<n>` with the image tag pinned to that SHA and the HTTPRoute rewritten to `<repo>-pr-<n>.<domain>`; a Kyverno policy stamps a ResourceQuota + LimitRange on every preview namespace, and closing the PR prunes the Application, its resources and its namespace (no reaper job). `app-ci` was extended to build PR heads and tag every image `:latest` **and** `:<commit sha>`, and the golden-path skeletons ship the `preview/` overlay. Previews are deliberately unauthenticated-but-internal (a per-PR hostname would need a per-PR OIDC client). ADR-0017 records the deltas; [User Guide §4](USER_GUIDE.md#preview-environments) documents the flow. **LIVE-VERIFIED on DigitalOcean (2026-09-13)** — a throwaway `adhar/preview-demo` Gitea repo with a `preview/kustomization.yaml`, one PR labelled `preview`: the ApplicationSet generated `preview-demo-pr-1` in under 30 s, created namespace `preview-preview-demo-1` labelled `adhar.io/plane: preview` + `adhar.io/preview: true`, Kyverno stamped `preview-quota` and `preview-limits` on it, and **the PR head was what deployed, not the base branch** (the PR's `replicas: 2` change was live). Adding an HTTPRoute to the overlay produced `preview-demo-pr-1.platform.adhar.io`, which answered **HTTP 200**. Closing the PR pruned the Application and every resource it owned within ~60 s, with no reaper job. **This uncovered a fatal bug that had to be fixed first**: the Application template set the finalizer `resources-finalizer.argoproj.io`, but ArgoCD honours only `resources-finalizer.argocd.argoproj.io` — with the `argocd.` segment. The API server stores any finalizer string, so the short name was accepted and then removed by nobody: the ApplicationSet controller logged `generated 0 applications` and `Deleted application` every single minute while the Application sat in Terminating for 12+ minutes (`process_finalizers_ms=0`) and **nothing was ever pruned**. The same wrong name was in all four main ApplicationSets (`adhar-appset-{local,production,gitops,workload}.yaml`) and in the DataPlane controller's vcluster Application, so deleting *any* platform Application would have hung the same way; all six are corrected and the Go path now uses `globals.ArgoCDResourcesFinalizer`. One caveat worth keeping in mind rather than fixing: the *namespace* is pruned only when the overlay declares it as a managed resource — a namespace created solely by `CreateNamespace=true` is unmanaged and stays behind. The appset's own comment says this and the four golden-path skeletons all declare their Namespace; a hand-rolled overlay that omits it leaves an empty namespace
- 🟡 **Supply-chain policies**: the ADR-0019 staged rollout is now a real switch, not a comment. The three policies (signature verification, no-`:latest`, registry allowlist) moved out of `kyverno-policies` into their own `security/supply-chain-policies` package and ship **twice** — `manifests/audit/` (enabled everywhere, the default) and `manifests/enforce/` (wired `enabled: "false"`, the knob), identical rules differing only in `failureAction` (plus digest pinning, which Kyverno forbids on a non-enforcing rule), so **Audit findings predict exactly what Enforce would block**. Enforcing an environment is one line in `adhar-appset-<env>.yaml` + the mirrored `environments/<env>/config.yaml`; policy names carry an `-enforce` suffix so both packs coexist. **The attestor now matches what the platform actually produces**: the Tekton `cosign-sign` Task signs **with a key** (`--key=k8s://adhar-system/cosign-key --tlog-upload=false`) from a durable, platform-owned keypair generated once by the `cosign-keygen` Sync-hook Job — so the policy reads that Secret via a `keys.secret` attestor with `rekor.ignoreTlog: true` (the previous policy pointed at `rekor.sigstore.dev`, which would have failed *every* platform-built image the moment it enforced), with the GitHub Actions **keyless** identity kept as an `any`-alternative (`count: 1`) for the `ghcr.io/adhar-io/*` images `.goreleaser.yaml` `docker_signs` signs. `adhar-system`/`kube-system` (and the rest of the platform namespaces, plus anything labelled `adhar.io/plane: control`) are excluded from every rule, twice over — by name and by label — so an Enforce flip cannot brick the platform. `hack/verify-supply-chain.sh` is the drill: throwaway cosign keypair → two tiny public images copied into the platform Harbor → sign one → Enforce ClusterPolicy scoped to a scratch namespace with `failurePolicy: Fail` → assert unsigned DENIED / signed ADMITTED → clean up everything. scanning in the pipeline is a Tekton `trivy-scan` Task running `aquasec/trivy` directly, so the gate does not depend on the `security/trivy` operator package (which stays wired-but-disabled in every profile — an earlier draft of this line claimed it was enabled in production; it is not); cosign's policy-controller runs in the shared `adhar-system` namespace like every other package (ADR-0011) — the `Secret/webhook-certs` collision it used to have with Tekton is resolved by renaming *Tekton's* secret through `WEBHOOK_SECRET_NAME` and pinning its `WEBHOOK_PORT`, and the one package that cannot follow (kpack/buildpack hardcodes the same secret name in its binary) keeps `kpack-system`. **The drill has now been run, twice, on a live DigitalOcean cluster (2026-09-13) and PASSES**: Kyverno reaches `harbor.platform.adhar.io`, parses a key-based cosign signature made with `--tlog-upload=false`, and enforces it at admission — unsigned image DENIED, signed image ADMITTED — which is exactly the signature the Tekton `cosign-sign` Task produces, so `security/supply-chain-policies/manifests/enforce` is safe to enable. Getting there took three fixes to `hack/verify-supply-chain.sh`, each a defect that would have made the drill lie: (1) it stripped the scheme off `EXT_ENDPOINT` with a BRE `\?`, which **BSD sed reads as a literal '?'**, so on macOS — where the drill is usually run — `HARBOR_HOST` kept its scheme and every URL became `https://https://harbor…`, failing as an unreachable-registry error pointing nowhere near the cause; (2) it polled `.status.ready` on the ClusterPolicy, a field current Kyverno no longer sets (it reports a standard `Ready` **condition**), so the drill declared a policy that was in fact Ready to be broken; (3) it pushed its images into Harbor's `library/` project — which the platform's own `verify-supply-chain-images` policy Enforces against the **platform's** cosign key — so the drill's throwaway-key signature was rejected by a platform policy while the failure was reported against the drill's own. The drill now provisions and tears down its own `adhar-drill` Harbor project, making it genuinely independent of platform policy as it always claimed to be. It also no longer depends on `cosign copy`, which is unusable in cosign v2.4.2 (it validates `--only` even when the flag was never passed); the copier is now crane/skopeo/cosign, whichever is present. Cleanup verified complete (project 404, namespace gone) and a second consecutive run passed identically. **✅ The enforce pack is now ENABLED in the production profile and verified live (2026-09-13)**: with the three `-enforce` ClusterPolicies Ready, a scratch workload namespace was used to confirm each behaviour — a `:latest` tag is **DENIED** (`An explicit image tag is required`), a registry outside the allowlist is **DENIED** (`Image registry is not in the platform allowlist`), an unsigned image in the platform Harbor is **DENIED** by signature verification, an allowed registry with an explicit tag is **ADMITTED**, and a platform namespace is correctly **EXCLUDED** (a `:latest` pod in `adhar-system` is admitted), so the flip cannot brick the platform. One note for anyone reading the policy: `docker.io` *is* on the allowlist, so a docker.io image being admitted is correct rather than a gap.
- 🟡 **Platform auth CLI**: `adhar auth login/logout/token/whoami` against the `adhar-cli` Keycloak client (persisted sessions, auto-refresh); Keycloak groups → Kubernetes RBAC bindings shipped. **The Keycloak half is live-verified on DigitalOcean (2026-09-13)**: the full session lifecycle works end to end — `login` authenticates against the real realm and reports the `groups` claim, `whoami` shows identity/groups/roles/issuer, `token` prints a valid JWT, `logout` invalidates the server-side session *and* removes the local credential file, after which `token` refuses instead of serving a stale one; `user1@noreply.com` resolves to `platform-admin` and `user2@noreply.com` to `platform-developer`, and re-login restores the session. Four defects were found and fixed while verifying it: (1) **`adhar auth token` wrapped the token in the CLI banner and footer on stdout**, so the documented `kubectl --token "$(adhar auth token)"` and `curl -H "Authorization: Bearer $(adhar auth token)"` both captured the chrome along with the credential and could never have worked; (2) more broadly, **the logger wrote its `INFO:` diagnostics to stdout**, so *no* `adhar … -o json` output anywhere in the CLI was parseable — `get status`, `get apps`, `get environments`, `get all` and `auth token` all emitted a log line ahead of the JSON document. Both are fixed by one rule in `cmd/root.go`: when a command's stdout is machine-readable (`-o json|yaml`, or a command annotated `adhar.io/plain-output` such as `auth token`) the header/footer are suppressed and the logger is redirected to stderr — payload on stdout, diagnostics on stderr. Use cases that turn adopters into references.

- 🔜 **Multi-tenancy hardening**: vcluster-per-team self-service (`CompositeCluster` vcluster composition), hierarchical quotas, tenant-scoped observability views
- 🔜 **Hostile-tenant isolation**: Kamaji hosted control planes with dedicated node pools for regulated workloads
- 🔜 **Air-gapped installation**: image bundle + private Sigstore + offline chart pipeline as a first-class install mode
- 🔜 **Compliance evidence**: continuous CIS/SOC2 posture from Kubescape/Kyverno reports, exportable as auditor-ready artifacts
- 🔜 **Cost governance**: OpenCost budgets with alerts and showback/chargeback reports per team/namespace/cluster
- 🔜 **Managed upgrades at fleet scale**: `adhar upgrade` across registered workload clusters with canary waves and automatic rollback on health regression
- 🔜 **Identity federation**: enterprise IdP (AD/Okta/Entra) federation recipes into Keycloak with SCIM-style group sync

## Cross-Cutting Commitments

- **No breaking changes without an ADR** and a documented migration
- **Local–production parity is sacred** — nothing lands in T2/T3 that can't be exercised (scaled down) in T1
- **Every feature ships with docs** — the [docs set](README.md) is part of the definition of done
- **APIs graduate deliberately**: `v1alpha1` → `v1beta1` once controllers are in-cluster and covered by e2e
- **🟡 → ✅ requires a live run**: Phase 1/2 items graduate only after a real cloud provisioning + multi-cluster exercise; a standing verification checklist lives with each phase's PRs
