# Adhar Roadmap

Direction, not commitment — sequencing follows community needs. Discuss on [GitHub Discussions](https://github.com/adhar-io/adhar/discussions).

The destination is fixed: the best open-source Internal Developer Platform — one command to a complete, production-grade, customizable platform on any infrastructure. The [Architecture](ARCHITECTURE.md) describes the target design (topologies T1→T3); **this roadmap is the main tracker** — every capability is listed under its phase with its current status.

**Legend**: ✅ implemented and exercised · 🟡 implemented, needs live verification/hardening · 🔜 designed, not yet built

---

## Phase 0 — Local Excellence (v0.1.x) ✅ COMPLETE

The foundation everyone evaluates first: `adhar up` on a laptop must be flawless.

- ✅ Deterministic bootstrap: Gateway API → Cilium → Gateway → ArgoCD → Gitea
- ✅ GitOps package model: full catalog wired, curated local core enabled
- ✅ Crossplane v2 control plane (23 XRDs, 34 Compositions) packaged and installable
- ✅ Automated releases (GoReleaser + GitHub Actions: binaries, GHCR images, Homebrew)
- ✅ Standard status conditions on `AdharPlatform` (ArgoCDReady, GatewayReady, GiteaReady, CrossplaneReady, GitOpsReady, aggregate Ready) with reconcile-failure messages, surfaced by `adhar get status`
- ✅ Unit test suite fully green (was ~15 known-failing tests; fixes included restoring the `adhar://` source-replication feature, source-deletion mirroring to Git, tag/branch checkout, secret patching, and scheme gaps)
- ✅ Package health dashboard: `adhar get status` shows per-package ArgoCD health/sync with a healthy/progressing/degraded summary
- ✅ E2E test covering the full bootstrap sequence (`make e2e`): `adhar up` → Ready condition → foundation components (deployments, pinned Gateway node ports, CRDs) → seeded Gitea repos via the external route → ArgoCD API auth → ApplicationSet package health → CLI status → `adhar down`

## Phase 1 — Single-Cluster Production (T2) ✅ VERIFIED (DigitalOcean, 2026-09)

Make one managed cluster a defensible production platform. Every item below was exercised on a real DigitalOcean cluster (kubeadm, HA mode, 1 control plane + 10 workers, full production catalogue) in September 2026; the one 🟡 left is the node autoscaler, whose live scale-up/down run still needs a DigitalOcean token (the cloud API path is the same one `adhar cluster scale` already proved).

- ✅ **Self-managed clusters on raw cloud compute (kubeadm) — DigitalOcean live-verified**: all six providers (AWS EC2, Azure VMs, GCP GCE, DigitalOcean droplets, Civo instances, custom BYO hosts) provision plain Ubuntu machines and bootstrap Kubernetes with kubeadm over SSH — containerd, kube-proxy skipped (Cilium from the platform bootstrap replaces it, matching the Kind flow); managed services (DOKS, Civo k3s) opt-in via `useManagedK8s: true` with otherwise identical behaviour. Live on DO (2026-09): **clean `--recreate` → 1 control plane + 10 workers + full platform bootstrap in ~18 min**, worker scale-up (join) / scale-down (drain), LB + wildcard TLS + DNS all automatic. Node prep now also hardens the node itself — static upstream resolvers (the systemd-resolved stub dying wedged every containerd image pull cluster-wide) and raised inotify/file-descriptor limits (controller managers were dying with "too many open files" on dense nodes). Single control-plane today (HA control planes with LB + stacked etcd are the next step)
- ✅ **In-cluster controllers (DigitalOcean live-verified 2026-09)**: `adhar controller` runs the manager as a Deployment (leader election, health probes); installed by `adhar up --in-cluster` and by default on cloud bootstraps. It runs the released image matching the CLI (`ghcr.io/adhar-io/adhar:<version>`; dev builds track `:latest`) — verified holding the lease and reconciling the DataPlane API on the cloud cluster (dev code exercised via a Harbor-hosted build of the same image)
- ✅ **HA mode end-to-end (DigitalOcean live-verified 2026-09)**: `enableHAMode` flows config → `AdharPlatform` CR → HA manifest variants: ArgoCD application-controller ×2, redis-ha ×3 + haproxy ×3, server/repo-server HPAs + PDBs; Gitea on a bootstrap-phase CNPG cluster (`gitea-db`, 2 instances, no bundled PostgreSQL), Keycloak on CNPG (`keycloak-db`, 2 instances in HA via the seed-time template); Crossplane HA variant selected. Fixed on the way: the HA ArgoCD variant had `server.insecure: false` (redirect loop behind the Gateway). Remaining: Gitea itself is 1 replica behind a PDB; HA *control planes* (multi-master) are still the next step
- ✅ **Production edge (DigitalOcean live-verified 2026-09)**: cloud Gateway variant (LoadBalancer, wildcard listener) with the issuer chosen by the platform spec; DNS provider derived from the cloud (or `globalSettings.dnsProvider`), credentials materialised by the CLI into the `adhar-dns-provider` Secret; external-dns publishes every HTTPRoute hostname in the platform zone; cert-manager issues the `*.<host>` wildcard via DNS-01 (`adhar-letsencrypt-dns`, rendered per provider from `cluster-issuers.yaml.tmpl`); the whole stack is templated at seed time (`*.yaml.tmpl`) with no hardcoded host/email/cloud; console reachable at `https://console.<host>` on a real domain
- ✅ **SSO by default**: Keycloak OIDC wired into ArgoCD, Gitea, Grafana, Console, Kargo (native), and every other platform UI through a generated oauth2-proxy front (`hack/gen-sso.sh` → `sso.yaml`); Keycloak clients are provisioned generically from labelled ConfigMaps (`adhar.io/keycloak-client`) by the config job plus a 5-minute reconcile CronJob, so a new package gets SSO by shipping one ConfigMap; `credential-rotation` rotates bootstrap credentials into Vault break-glass and the foundation/`adhar upgrade` honour the rotated `gitea-credential`
- ✅ **Applications consume platform capabilities, never bundle their own**: one Strimzi **Kafka in KRaft mode** (`adhar-kafka`, no ZooKeeper anywhere), one MinIO (per-app buckets provisioned from `data/minio/values.yaml`), CNPG for PostgreSQL, Valkey for cache, OpenSearch for search, ClickHouse Keeper where a chart wants ZooKeeper. Bundled subcharts are stripped in each package's `generate-manifests.sh` so the wiring survives chart regeneration — this removed a duplicate Kafka+ZooKeeper (PostHog) and a duplicate MinIO (Kubeflow Pipelines), both of which had also rotted upstream (deleted Bitnami / gcr.io images)
- ✅ **Backup/DR (DigitalOcean live-verified 2026-09)**: Velero Schedules (daily platform / weekly cluster) with the node agent deployed and file-system backups on by default + CNPG WAL archiving and daily base backups for platform databases, all into the platform MinIO (`adhar-backups`; Velero under its own `velero/` prefix, CNPG under `cnpg/`). Drill run: on-demand backup → restore into a scratch namespace recreated the Kargo project intact. Off-cluster object storage (DO Spaces/S3) is a BackupStorageLocation swap; runbook in [Production §5](PRODUCTION.md#5-backup-and-disaster-recovery)
- 🟡 **Node autoscaling (scale on demand, no big cluster up front)**: `environments[].autoscaling` (min/max workers) turns the worker count into a range — the in-cluster manager runs a platform-native node autoscaler (`platform/controllers/autoscaler`), because the upstream cluster-autoscaler has no provider for self-managed kubeadm clusters on raw cloud compute. It adds a worker when pods are `Pending` for capacity (never for taints/affinity/volume reasons) through the same provider path as `adhar cluster scale`, and drains + removes the emptiest worker when cluster-wide requested CPU **and** memory stay under the threshold (default 50%) for the scale-down delay (default 10m), skipping nodes with ReadWriteOnce volumes or uncontrolled pods; bounded by min/max with a scale-up cooldown, one node per tick, reported on `AdharPlatform.status.autoscaling` and as Events. Unit-tested end to end; **a live scale-up/scale-down run on DO is what remains for ✅** — blocked only on a valid DigitalOcean API token (revoked mid-run); the cloud call is the one `adhar cluster scale` already proved live
- ✅ **Upgrade story (DigitalOcean live-verified 2026-09)**: `adhar upgrade` converges the foundation through the real reconcilers (now including the Crossplane control-plane configuration — XRDs, Compositions, Functions, provider packages, Operations — re-applied on every upgrade), diffs the local stack against the GitOps repos (`--diff-only`, `--yes`), pushes and refreshes on confirm; exercised five times in a row to roll fixes onto the live cluster

## Phase 2 — Multi-Cluster Platform (T3) 🟡 IMPLEMENTED, PARTLY VERIFIED

The management cluster earns its name. Live-verified on DigitalOcean (2026-09): control-plane/data-plane separation (vcluster + adopt), the thin workload profile, observability out of the box. Still 🟡 — and the reason is the same for all of them — are the two items that need a **second real cluster on cloud compute**: *Workload clusters via GitOps* (a `CompositeCluster` provisioning DOKS) and *Cilium Cluster Mesh* (two Cilium clusters). Both, like the Phase 1 node autoscaler, are code-complete, render-/unit-verified, and blocked only on a valid DigitalOcean API token (the one used for this run was revoked mid-session). The verification recipe, in order, once a token exists: `adhar up -f config.yaml --env dev` with `autoscaling` on → schedule an unschedulable pod and watch `AdharPlatform.status.autoscaling` add a worker, then drain it back; apply `examples/`-style `CompositeCluster` (DOKS) and wait for `Ready` + the `cluster-<name>` ArgoCD Secret; create a `DataPlane` with `mode: composite` and check `MeshJoined`.

- ✅ **Control-plane / data-plane separation (vcluster + adopt live-verified 2026-09)** ([ADR-0023](adr/0023-control-dataplane-separation.md), [plan](design/0023-control-dataplane-separation.md)): the `DataPlane` API and controller are real end-to-end for `mode: vcluster` (the controller installs a vcluster through an ArgoCD Application, mirrors its kubeconfig, registers it with ArgoCD, wires the observability hub, and reports `Ready`) and `mode: adopt` (existing kubeconfig); both reached `Ready=True` on the cloud cluster, the thin profile landed on the plane, `adhar get dataplanes` lists them and `adhar get status` shows the fleet roll-up now kept on `AdharPlatform.status.fleet`. `mode: composite` builds an XRD-valid `CompositeCluster` (composition selection under `spec.crossplane.*`, the Crossplane v2 form) but awaits a cloud-API run. The controller watches only core types, so it is registered unconditionally (no more cache-sync death). Still 🟡 inside this item: the mesh phase (gated on a real `cilium clustermesh connect` Job — see Cluster Mesh below), Sveltos placement in the `environments` repo, `control-plane-no-apps` shipped but disabled, no envtest yet
- 🟡 **Workload clusters via GitOps**: all five cloud `CompositeCluster` compositions auto-register clusters with ArgoCD (EKS via IAM `awsAuthConfig`, GKE via `argocd-k8s-auth gcp`, AKS/DOKS/Civo via provider kubeconfig parsing). 2026-09: every composition rewritten to the real `function-go-templating` input (`GoTemplate`, was an invalid `FunctionIO` shape) and render-verified with `crossplane render`; provider packages moved to `xpkg.crossplane.io/crossplane-contrib` (Upbound `v2.x` packages are UXP-only), DigitalOcean onto `provider-upjet-digitalocean` v1.0.2, only the platform's own cloud installed by default, credentials materialised by `adhar up`. 2026-09: the DOKS composition is now **on the upjet provider** — namespaced MRs `kubernetes.digitalocean.m.crossplane.io/v1alpha1` `Cluster`/`NodePool` (the v1.0.2 package ships the `.m` kinds, so DOKS no longer needs the legacy cluster-scoped escape hatch a namespaced XR cannot use anyway), `nodePool` as a list of blocks, a `ClusterProviderConfig` named `default` reading a JSON credential, and the kubeconfig + ArgoCD cluster Secret built from upjet's flattened connection details (`attribute.kube_config.0.raw_config|host|cluster_ca_certificate|token`), stamped with the DataPlane labels (`adhar.io/cluster`, `adhar.io/dataplane`, `adhar.io/dataplane-mode: composite`) and published where the DataPlane controller looks for it (`<name>-kubeconfig` in `adhar-system`). Render-verified with `crossplane render` and schema-validated against the provider's own CRDs; **only the live run remains** (blocked in-session: the DigitalOcean API token is revoked). The kind composition is live-verified by the drill below
- ✅ **Thin workload-cluster profile (live-verified 2026-09)**: `adhar-appset-workload.yaml` deploys the agent set (kyverno + policies, alloy, the **external-secrets** agent, and metrics-server on planes with real kubelets — vcluster planes serve `metrics.k8s.io` through vcluster's host proxy instead) onto every ArgoCD-registered data plane (`adhar.io/cluster` label, stamped by both registration paths); monitoring CRs are excluded on data planes (no Prometheus Operator there) and the hub endpoints written by the DataPlane controller are respected (`RespectIgnoreDifferences`). Verified Healthy on the vcluster plane
- ✅ **Observability out of the box**: every package that exposes metrics ships a ServiceMonitor/PodMonitor and a Grafana dashboard (`kube-prometheus/manifests/dashboard-*.yaml`), Prometheus selects all monitors cluster-wide; Alloy ships metrics/logs/traces (cluster-labeled) to hub endpoints from the `observability-hub` ConfigMap; mimir/loki/tempo ingestion HTTPRoutes (SSO-fronted with bearer passthrough for spokes)
- 🟡 **Cilium Cluster Mesh + SPIFFE**: mesh-ready identity (`adhar-mgmt`/ID 1) baked in; the clustermesh-apiserver manifest ships in the foundation (`resources/cilium/clustermesh.yaml`, applied on demand) and the DataPlane controller's mesh phase now runs a real `cilium clustermesh connect` Job with a two-context kubeconfig and reports `MeshJoined` only on Job success. Honest status: not exercised on a live fleet yet, SPIRE is **not** deployed (`authentication.mutual.spire.enabled: false` — it starved the operator's Gateway controller), and vcluster planes share the host CNI so the mesh is meaningless there. Needs a real second Cilium cluster (shared `cilium-ca`, distinct cluster-id, non-overlapping Pod CIDRs)
- ✅ **Environment promotion (live-verified 2026-09)**: Kargo pipeline (Warehouse on the `environments` repo; staging auto-promotes, production requires approval; a promotion is a Git commit). Drill: a commit to `development/` produced Freight, staging auto-promoted and `promote: development -> staging` landed in the repo while production stayed unpromoted. Fixed on the way: Kargo ≥1.3 `ProjectConfig`, path-prefix vs glob `includePaths`, credentials over the in-cluster HTTP Gitea
- ✅ **Cluster reconstructability SLO (live-verified 2026-09)**: monthly drill CronOperation + observer WatchOperation measuring time-to-Ready against the 1-hour SLO (Crossplane Operations enabled on the running platform). A forced run composed the drill cluster in **17 s** and the observer recorded `verdict: pass`. Fixed on the way: the drill XR now selects its composition the Crossplane v2 way (`spec.crossplane.compositionSelector`) and the kind composition composes only namespaced resources with proper readiness markers

## Phase 3 — Developer Experience & Ecosystem (IN PROGRESS)

From platform to product.

- ✅ **Paved-road CI (Tekton `app-ci`)**: the supply-chain package ships the CI EventListener + pipelines (Gitea webhook → buildpacks/Dockerfile build → cosign sign → trivy scan → Harbor → GitOps version-bump), driven by each service's `.adhar/app.yaml`; library releases publish to Nexus (`adhar-kit`, `adhar-ui` verified green); the Jenkins X / Lighthouse layer was removed (ADR-0018 superseded)
- 🟡 **Preview environments**: PR-generator ApplicationSet template ([examples/preview-environments-appset.yaml](../examples/preview-environments-appset.yaml), ADR-0017) + documented local-first workflow ([User Guide §4](USER_GUIDE.md#4-deploying-your-applications))
- 🟡 **Supply-chain policies**: Kyverno pack (signature verification, no-latest-tag, registry allowlist — Audit mode, ADR-0019 staged rollout); trivy enabled in production; **cosign own-namespace re-render is complete** — the policy-controller now installs into its own `cosign-system` namespace (`generate-manifests.sh` re-templated; CONFLICTS.md updated), resolving the `Secret/webhook-certs` collision with tekton and the `WEBHOOK_PORT` service-link hijack, so cosign is now **enabled in production** for keyless signature verification. A live signed-image enforcement run is what remains for ✅
- 🟡 **Platform auth CLI**: `adhar auth login/logout/token/whoami` against the `adhar-cli` Keycloak client (persisted sessions, auto-refresh); Keycloak groups → Kubernetes RBAC bindings shipped
- 🟡 **Full production enablement**: provider-selected ApplicationSets — Kind gets the curated core, cloud/on-prem gets the full catalog (69+ enabled; conflicts documented inline)
- 🟡 **Golden paths**: `microservice` (Go service with health/ready endpoints, graceful shutdown, distroless image, hardened manifests + HTTPRoute, ADR-0018 pipeline stub), `frontend` (nginx-unprivileged static site, same manifest set), and now a **`data-pipeline`** paved road (Backstage scaffolder template: Dagster job → Iceberg REST catalog, dbt-trino models, on-platform manifests + `jenkins-x.yml`, aligned to the ADR-0020 lakehouse direction) shipped in `application/adhar-templates` and wired into the Console catalog; Console scaffolding *execution* integration and the ML (Kubeflow/MLflow) path still 🔜
- 🟡 **Score cards**: per-service production-readiness scoring, surfaced in the Console. `application/scorecards` ships a read-only scorer CronJob that grades each service 0–100 (A–F) from real in-cluster signals (ArgoCD app health/sync, probes + resource requests, HTTPRoute exposure, backup presence, Kyverno PolicyReport pass rate, no-`:latest`), writes an `adhar-scorecards` ConfigMap, and exposes a Backstage entity annotation. Tunable weights (reliability/security/observability/operations). Enabled in the production set; a live scoring run over a running fleet is what remains for ✅
- 🟡 **Package marketplace**: community-contributed packages with a compatibility contract and provenance (signed, scanned). The contract is defined and validated: `marketplace.schema.json` (draft-07 — category, `adharCompatibility` range, dependencies, provenance, planeAffinity, stability tiers), `MARKETPLACE.md` (submission + promotion flow, ADR-0019 provenance pillars), three conforming example `adhar-package.yaml` contracts, and `hack/validate-packages.sh` (passes). Remaining for ✅: roll `adhar-package.yaml` to all ~87 packages, wire the validator into CI, and emit SBOM/attestation artifacts from the release pipeline
- 🟡 **Policy packs**: `security/policy-packs` package ships CIS- and SOC2-oriented Kyverno ClusterPolicy profiles (labeled `adhar.io/policy-pack: cis|soc2`, all Audit mode), plus the **plane-isolation** policy (`control-plane-no-apps`, ADR-0023 §6) that keeps application workloads off the control plane; wired disabled-by-default in the ApplicationSet as an opt-in
- 🟡 **Agentic platform (Adhar AI)** ([ADR-0024](adr/0024-agentic-ai-platform.md), [plan](design/0024-agentic-ai-platform.md)): a fully agentic Adhar — configure one LLM key and the platform can investigate, explain, scaffold, provision, and remediate, **through** its existing control surfaces, never around them. The **control-plane package is scaffolded** (`ai/adhar-ai/`, opt-in / disabled by default so the platform runs unaffected until keyed); the runtime/gateway/MCP container images live in the separate `adhar-io/adhar-ai` Python repo (not yet published — that's the gate to ✅):
  - 🟡 **MCP-native tools**: per-domain MCP servers (cluster, gitops, provision, observability, security, cost, catalog) manifested as distinct Deployments+Services with read tools RBAC-scoped (read-only `adhar-ai` ServiceAccount) and **write tools that only open Gitea PRs** — no direct `kubectl apply`/cloud-mutation path; exposed outward (Gateway + OIDC at `mcp.adhar.localtest.me`) so external agents (Claude Code, IDEs, ChatOps) drive Adhar through identical governed tools
  - 🟡 **GitOps-safe agent runtime**: `adhar-ai-runtime` Deployment + `adhar-ai-config` staged-autonomy ConfigMap (read-only → suggest → approve-to-apply → scoped, default `suggest`) with the event-driven operators (alert-triage, drift-explain, cost-advisor, upgrade-preflight) declared — every change lands as a reviewable, revertible Git PR
  - 🟡 **Provider-agnostic LLM gateway**: `adhar-ai-llm-gateway` Deployment reads one secret (`adhar-ai-llm`, Vault→ESO) selecting Claude (default, latest models) / OpenAI / Azure / OpenAI-compatible / Ollama (air-gapped); token/rate budget knobs central
  - 🟡 **Grounding & governance**: pgvector RAG (CNPG `adhar-ai-rag`) over docs/ADRs/runbooks + live state; Keycloak `adhar-ai` OIDC client, a Kyverno `adhar-ai-guardrails` policy on agent actions (Audit), and an `adhar.io/origin: adhar-ai` provenance label; platform runs unaffected when uninstalled or unkeyed

## Phase 4 — Data & Intelligence Platform

The lakehouse and ML story on top of the platform substrate (ADR-0020).

- 🔜 **Iceberg REST catalog service**: one platform-operated catalog (CNPG-backed) as the multi-engine interoperability point; buckets self-service via Crossplane XRs
- 🔜 **Data golden path**: Airbyte → Iceberg → dbt/Trino → Dagster scaffolded like app golden paths; lakeFS branches as "preview environments for data"
- 🔜 **Table maintenance as day-2**: compaction/snapshot-expiry/orphan-cleanup CronOperations shipped with per-table defaults
- 🔜 **ML workflow**: Kubeflow/MLflow golden path with model registry, GPU node-pool support in `CompositeCluster`, and inference serving via the Gateway
- 🔜 **Governance**: OpenMetadata wired to the catalog for lineage/discovery/ownership out of the box

## Phase 5 — Enterprise Readiness & Scale

Use cases that turn adopters into references.

- 🔜 **Multi-tenancy hardening**: vcluster-per-team self-service (`CompositeCluster` vcluster composition), hierarchical quotas, tenant-scoped observability views
- 🔜 **Hostile-tenant isolation**: Kamaji hosted control planes with dedicated node pools for regulated workloads
- 🔜 **Air-gapped installation**: image bundle + private Sigstore + offline chart pipeline as a first-class install mode
- 🔜 **Compliance evidence**: continuous CIS/SOC2 posture from Kubescape/Kyverno reports, exportable as auditor-ready artifacts
- 🔜 **Cost governance**: OpenCost budgets with alerts and showback/chargeback reports per team/namespace/cluster
- 🔜 **Managed upgrades at fleet scale**: `adhar upgrade` across registered workload clusters with canary waves and automatic rollback on health regression
- 🔜 **Identity federation**: enterprise IdP (AD/Okta/Entra) federation recipes into Keycloak with SCIM-style group sync

## Cross-Cutting Commitments

- **No breaking changes without an ADR** and a documented migration
- **Local–production parity is sacred** — nothing lands in T2/T3 that can't be exercised (scaled down) in T1
- **Every feature ships with docs** — the [docs set](README.md) is part of the definition of done
- **APIs graduate deliberately**: `v1alpha1` → `v1beta1` once controllers are in-cluster and covered by e2e
- **🟡 → ✅ requires a live run**: Phase 1/2 items graduate only after a real cloud provisioning + multi-cluster exercise; a standing verification checklist lives with each phase's PRs
